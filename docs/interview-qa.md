## 0. 30초 요약 (제일 먼저 준비할 것)

> "사진 한 장으로 방 안의 가구를 3D로 떼어내고, 가구가 사라진 빈 방에서 그 가구들을 다시 배치해 보는 웹 서비스입니다.
> 기존 인테리어 앱이 '새 가구를 사서 놓아보는' 서비스라면, 저희는 반대로 **이미 가진 내 짐**을 옮겨보는 데 집중했습니다.
> 파이프라인은 4단계입니다. ① SAM2로 가구를 클릭 한 번에 분할 → ② LaMa + Stable Diffusion으로 가구를 지우고 배경을 복원 →
> ③ uLayout으로 방의 실제 치수(m)와 카메라 각도를 추정 → ④ SAM3D로 가구를 3D 메쉬로 변환해서 Three.js 위에 배치합니다.
> 백엔드는 FastAPI, 프론트는 React + Three.js이고, 환경이 충돌하는 모델 2개는 별도 포트의 사이드카 서버로 분리했습니다."

# A. 프로젝트 개요

### Q1. 프로젝트를 한 문장으로 소개해 주세요.
**답변:** 사진 한 장에서 가구를 3D로 분리하고, 가구가 지워진 빈 방 위에서 자유롭게 재배치해 보는 "역방향 인테리어 시뮬레이터"입니다.

**💡 쉽게 말하면:** 방 사진 찍으면 → 가구가 지워진 빈 방이 나오고 → 지워진 가구들이 3D 블록이 되어 옆에 쌓임 → 레고처럼 다시 배치.

---

### Q2. 왜 이 주제를 골랐나요? (기존 서비스와의 차별점)
**답변:** 기존 인테리어 앱(오늘의집 3D, IKEA Place 등)은 **카탈로그에 있는 새 가구**를 놓아보는 구조입니다.
그런데 실제로 사람들이 가장 자주 하는 고민은 "이 무거운 옷장을 저쪽으로 옮기면 어떨까"입니다.
직접 옮겨보지 않으면 알 수 없고, 옮겼다가 아니면 되돌리는 비용이 큽니다.
저희는 **내가 이미 가진 가구를 그대로 3D화**한다는 점에서 차별화됩니다. 카탈로그가 필요 없고, 사진 한 장이면 됩니다.

**💡 쉽게 말하면:** 남의 가구를 놓아보는 게 아니라, 내 가구를 옮겨보는 앱.

---

### Q3. 전체 아키텍처를 설명해 주세요.
**답변:** 프론트는 React + Vite, 3D는 Three.js를 직접 씁니다. 백엔드는 FastAPI 단일 서버(8001)에 라우터를 모델별로 나눴고,
환경 충돌이 있는 모델 두 개는 별도 프로세스로 띄운 **사이드카 서버**입니다.

| 포트 | 구성 | 역할 |
|------|------|------|
| 5173 | React + Vite | UI, Three.js 3D 뷰어 |
| 8001 | FastAPI (conda `sam3d`) | SAM2 / LaMa / SD / SAM3D — 메인 API |
| 8002 | uLayout 사이드카 | 방 치수 추정 + 실사 텍스처 rectify + 카메라 pose |
| 8003 | Omni3D 사이드카 | 벽걸이 가구 실제 크기 추정 |

4개 서비스는 `scripts/services.sh start` 한 방으로 뜨고, 포트 LISTEN 여부로 준비 완료를 판정합니다.

**💡 쉽게 말하면:** 메인 서버 하나 + 성격 안 맞는 모델 2개를 옆방에 따로 살게 한 구조. 서로 HTTP로 대화.

---

### Q4. 사용자 흐름(화면 단계)을 설명해 주세요.
**답변:** 4단계입니다.
1. **사진 업로드** — 아이폰 HEIC까지 지원
2. **가구 선택** — 캔버스에서 가구를 클릭하면 SAM2가 실시간으로 마스크 미리보기를 보여줌. 가구마다 라벨(소파/침대/…)을 붙임
3. **방 만들기** — 빈 방 이미지에서 벽·바닥 색/텍스처를 뽑고, 방 치수를 자동 추정
4. **3D 배치** — 가구를 3D로 변환하고 드래그해서 방에 배치, 회전·복사·크기 조절·저장

**💡 쉽게 말하면:** 올리고 → 찍고 → 방 만들고 → 배치. 화면 상단 진행바가 그대로 이 4개.

# B. 모델 선택 이유 (자주 나오는 질문)

### Q5. 왜 SAM2를 썼나요? SAM1이나 다른 세그멘테이션 모델은요?
**답변:** 세 가지 이유입니다.
1. **프롬프트 방식이 UX에 맞았습니다.** 사용자가 가구를 클릭 한 번 하면 그 지점이 포함된 객체를 분할해 줍니다. 카테고리를 미리 학습시킬 필요가 없습니다.
2. **Zero-shot 일반화** — 학습 데이터에 없던 가구(사용자 방의 특이한 서랍장 등)도 잘 잡습니다. YOLO 계열은 정해진 클래스만 잡습니다.
3. SAM2는 SAM1 대비 Hiera 백본으로 경계 품질과 속도가 개선됐습니다. 저희는 `sam2.1_hiera_large` 체크포인트를 씁니다.

**💡 쉽게 말하면:** "이 물건이 뭔지" 몰라도 "이 픽셀을 클릭했으니 여기 있는 덩어리"를 오려주는 모델. 그래서 가구 종류를 학습시킬 필요가 없음.

**꼬리질문 대비 — SAM2는 원래 비디오 모델 아닌가요?**
> 맞습니다. SAM2의 핵심 기여는 비디오 추적(메모리 어텐션)인데, 저희는 이미지 한 장만 쓰므로 `SAM2ImagePredictor`로 이미지 모드만 사용합니다.

---

### Q6. 마스크가 여러 개 나오는데(multimask_output) 어떻게 하나를 고르나요?
**답변:** 용도에 따라 기준을 다르게 뒀습니다.
- **빈 방 만들기용 마스크**(`segment.py`)는 SAM2가 주는 **confidence score가 가장 높은 것**을 선택합니다.
- **가구 추출용 마스크**(`extract.py`)는 **면적이 가장 큰 것**을 선택합니다.

이유는, SAM2는 같은 클릭에 대해 "손잡이 / 서랍 / 서랍장 전체"처럼 계층적으로 3개를 줍니다.
가구를 통째로 3D화해야 하니 부분이 아니라 전체가 필요했고, 실험해 보니 면적 기준이 "전체"를 훨씬 안정적으로 골랐습니다.

**💡 쉽게 말하면:** SAM은 "작게/중간/크게" 세 가지 답을 준다. 가구를 통째로 떼야 하니까 제일 큰 걸 고른 것.

---

### Q7. 왜 LaMa와 Stable Diffusion을 **둘 다** 썼나요? 하나로는 안 되나요?
**답변:** 둘의 장단점이 정확히 반대라서 직렬로 연결했습니다.
- **LaMa**는 Fourier Convolution 기반이라 **넓은 영역을 구조적으로 일관되게** 메웁니다. 벽/바닥처럼 큰 면을 지울 때 강합니다. 다만 결과가 흐릿하고 디테일이 뭉갭니다.
- **Stable Diffusion inpainting + ControlNet(Canny)**은 **질감을 사실적으로** 만들지만, 아무 제약 없이 돌리면 없던 가구를 상상해서 그려 넣습니다.

그래서 **LaMa로 먼저 구조를 채우고, 그 결과를 SD로 다듬는** 순서를 썼습니다. SD에는 Canny 엣지를 ControlNet 조건으로 줘서 원래 방의 선(몰딩, 걸레받이)을 유지시켰습니다.

**💡 쉽게 말하면:** LaMa = 벽지 대충 발라주는 도배공(빠르고 구조 안정, 근데 밋밋), SD = 그 위에 질감 살려주는 마감공(예쁘지만 냅두면 없는 가구를 그림). 그래서 순서대로 쓰고, SD에는 "이 선은 지키라"고 스케치를 쥐여줌.

---

### Q8. SD가 없던 가구를 그려 넣는 문제(hallucination)는 어떻게 막았나요?
**답변:** 네 가지 장치를 걸었습니다.
1. **negative prompt**에 `furniture, bed, chair, table, objects, clutter`를 명시
2. **ControlNet Canny 엣지 맵에서 마스크 영역의 엣지를 0으로 지웁니다.** 이게 핵심입니다 — 지워야 할 가구의 윤곽선이 엣지 맵에 남아 있으면 ControlNet이 그 윤곽을 따라 가구를 "복원"해 버립니다.
3. `controlnet_conditioning_scale=0.5`로 조건 강도를 절반만 줘서, 선은 참고하되 지나치게 따라가지 않게 했습니다.
4. 마스크에 **아래 방향 비대칭 커널로 dilate**를 추가했습니다. 가구 아래 생기는 그림자까지 지워야 완전히 빈 방처럼 보이기 때문입니다.

**💡 쉽게 말하면:** "가구 그리지 마"라고 말로만 하면 안 듣는다. 가구 윤곽선 자체를 스케치에서 지워버려야 안 그린다. 그리고 그림자도 같이 지워야 진짜 빈 방으로 보임.

---

### Q9. SAM3D는 무엇이고 왜 썼나요?
**답변:** Meta의 SAM 3D Objects입니다. **이미지 한 장(+마스크)에서 3D 메쉬를 복원**하는 모델입니다.
저희 요구조건이 "사진 한 장"이었기 때문에, 여러 장을 요구하는 NeRF/3DGS 계열이나 다시점 생성 모델보다 적합했습니다.
내부적으로 2단계입니다 — Stage1이 거친 voxel(3D 점 덩어리)을 만들고, Stage2가 그걸 정밀한 메쉬로 만듭니다.

**💡 쉽게 말하면:** 사진 한 장 주면 3D 모델 뱉어주는 모델. 원래 3D를 만들려면 사방에서 여러 장 찍어야 하는데, 그걸 한 장으로 때움.

---

### Q10. Zero123, TripoSR, Gaussian Splatting도 코드에 있던데요? (초기 `web/` 폴더)
**답변:** 초기에 여러 3D 복원 방식을 비교 실험했습니다.
- **TripoSR** — 빠르지만 가구처럼 큰 물체에서 디테일이 부족
- **Zero123** — 다른 각도 이미지를 생성하는 방식인데, 실제 방 사진처럼 잘린/가려진 가구에서 품질이 불안정
- **Gaussian Splatting / LucidDreamer→SuGaR 브릿지** — 시각 품질은 좋지만 메쉬가 아니라 점 구름이라 "충돌 판정하며 배치"에 쓰기 어렵고, 학습 시간이 오래 걸림

최종적으로 **SAM3D**를 택했습니다. 마스크를 직접 조건으로 받고, 저희가 이미 SAM2로 마스크를 만들고 있어서 파이프라인이 자연스럽게 이어졌습니다.

**💡 쉽게 말하면:** 후보 4개 써보고 제일 맞는 거 골랐다. 가우시안은 예쁘지만 "덩어리"가 아니라 "점 먼지"라서 부딪힘 계산이 안 됨.

# C. 가장 어려웠던 문제 (핵심! 이 파트를 제일 두껍게 준비)

### Q11. 가장 어려웠던 기술적 문제는 무엇이었나요?
**답변:** **"가구의 실제 크기(미터)를 어떻게 아느냐"**였습니다.

SAM3D가 만들어주는 3D 메쉬는 **정규화된 좌표계**입니다. 즉 모양은 맞는데 "이게 1m짜리 의자인지 2m짜리 옷장인지"는 모릅니다.
그런데 방을 4.5m × 3.5m로 만들어놓고 가구를 배치하려면 미터 단위 크기가 반드시 필요합니다.
잘못되면 침대가 방보다 커지거나, 옷장이 인형 크기가 됩니다.

그래서 **우선순위 폴백 체인** 4단계를 만들었습니다.

| 순위 | 방법 | 적용 대상 |
|------|------|-----------|
| 1 | 카메라 pose 기반 광선–바닥평면 교차 | 바닥에 닿는 가구 (침대/소파/책상…) |
| 2 | Omni3D (Cube R-CNN) 추정 | 액자/거울/조명/커튼 등 벽걸이 |
| 3 | SAM3D pose-decoder의 scale 값 | 위 둘이 다 실패한 경우 (시계/화분/꽃) |
| 4 | 방 가로 × 0.2 | 최후의 폴백 |

**💡 쉽게 말하면:** AI가 만든 3D 모델은 "모양"만 알고 "실제 크기"는 모른다. 크기를 알아내는 방법 4개를 순서대로 시도해서, 되는 걸 쓰는 구조.

---

### Q12. 1순위인 "카메라 pose 기반 광선–바닥평면 교차"를 설명해 주세요.
**답변:** 원근법을 역이용하는 방식입니다.

1. uLayout이 방의 코너를 검출하고 `solvePnP`로 **카메라의 위치와 각도**를 구합니다.
2. 가구 bbox의 **아래쪽 중앙 픽셀**을 "가구가 바닥에 닿는 지점"으로 봅니다.
3. 카메라에서 그 픽셀 방향으로 **광선을 쏴서 바닥 평면(Y=0)과 만나는 점**을 계산합니다. → 카메라로부터 그 가구까지의 **실제 거리(z)** 를 알게 됩니다.
4. 핀홀 카메라 비례식 `실제높이 = 픽셀높이 × z / fy`에 넣으면 실제 높이(m)가 나옵니다.

핵심은 **원근 보정**입니다. 단순히 "사진에서 방 높이의 절반이니까 1.25m" 식으로 계산하면, 카메라에서 먼 가구는 작게 찍히므로 실제보다 작게 나옵니다. 거리를 직접 반영하기 때문에 그 오차가 사라집니다.

**💡 쉽게 말하면:** 사진에서 같은 크기로 보여도, 멀리 있는 건 실제로는 더 큰 물건이다. "얼마나 멀리 있는지"를 먼저 계산해서 크기를 보정한 것. 눈에서 가구 발밑까지 레이저를 쏴서 바닥에 닿는 지점을 찾는다고 생각하면 됩니다.

**꼬리질문 대비 — 왜 bbox 아래 중앙인가요?**
> 가구가 바닥에 서 있다면 그 지점이 바닥과 닿는 점이라고 가정할 수 있기 때문입니다. 이 가정이 이 방법의 유일한 전제이자 한계입니다.

---

### Q13. 그럼 바닥에 안 닿는 가구(액자, 조명, 커튼)는요? — Omni3D 도입 이유
**답변:** 12번 방법은 "가구가 바닥에 닿는다"는 가정 위에 있습니다.
액자·거울·벽걸이 조명·커튼은 공중에 떠 있어서 bbox 아래쪽이 바닥이 아니라 **벽 중간**을 가리킵니다.
그대로 계산하면 광선이 훨씬 먼 바닥에 꽂혀서 크기가 몇 배로 뻥튀기됩니다.

그래서 이 카테고리는 **아예 1순위를 시도하지 않고 건너뛰도록**(`THIN_FLAT` 리스트) 만들고, 대신 **Omni3D / Cube R-CNN**을 도입했습니다.
Omni3D는 2D 사진에서 물체의 3D 바운딩 박스(가로·세로·깊이 m)를 직접 예측하는 모델입니다.
저희는 이미 SAM2로 정확한 bbox를 알고 있으므로, 탐지 단계를 건너뛰고 **bbox를 정답으로 주입(oracle 2D)** 해서 크기 예측만 받아옵니다.

**💡 쉽게 말하면:** "발밑을 찾아 거리를 재는" 방법은 발이 바닥에 있어야만 통한다. 벽에 걸린 액자는 발이 없다. 그래서 이런 애들만 크기를 직접 맞혀주는 다른 모델을 붙였다.

**꼬리질문 대비 — 왜 커튼도 THIN_FLAT에 넣었나요?**
> 커튼은 바닥까지 닿는 제품도 있고 창턱에서 끝나는 제품도 있어서 "닿는다"는 가정 자체가 불안정합니다. 실측해 보니 편차가 커서 Omni3D 경로로 넘겼습니다.

### Q14. Omni3D도 못 하는 카테고리가 있다던데요?
**답변:** Omni3D 실내 체크포인트는 38개 클래스인데, **시계·화분·꽃은 그 taxonomy에 아예 없습니다.**
카테고리 목록을 직접 조사해서 확인한 뒤, 지원 목록(`OMNI3D_SUPPORTED`)을 코드에 명시하고
미지원 카테고리는 사이드카가 `unsupported: true`로 즉시 응답하도록 만들었습니다. 이 경우 3순위인 SAM3D scale 값으로 넘어갑니다.

**답변에서 강조할 포인트:** "안 되는 걸 몰라서 방치"가 아니라 **"안 된다는 걸 확인하고 폴백 경로를 명시적으로 설계"** 했다는 점입니다.

**💡 쉽게 말하면:** 그 모델이 아는 물건 목록에 '시계'가 없다. 그래서 시계는 아예 물어보지도 않고 다음 방법으로 넘어가게 했다.

### Q15. 왜 사이드카(별도 서버) 구조를 썼나요? 그냥 한 프로세스에 넣으면 안 되나요?
**답변:** **의존성 충돌** 때문입니다.
- 메인 백엔드(SAM2/LaMa/SD/SAM3D)는 비교적 최신 PyTorch 스택
- **uLayout**은 특정 numpy/opencv/torch 조합을 요구
- **Omni3D**는 legacy Detectron2 + PyTorch3D 스택 (Python 3.10)

한 가상환경에 다 넣으려다 버전 충돌로 실패했고, conda 환경을 3개로 분리한 뒤 **HTTP로 통신하는 사이드카 패턴**을 택했습니다.
부가 효과도 있었습니다 —
1. 사이드카가 죽어도 메인 서비스는 살아 있고, `success: false`를 받아 폴백으로 동작합니다.
2. 모델을 매 요청마다 로드하지 않도록 상주 서버로 만들어 응답 속도를 유지했습니다.

**💡 쉽게 말하면:** 세 모델이 요구하는 라이브러리 버전이 서로 안 맞아서 한 집에 못 산다. 그래서 각자 집을 주고 전화(HTTP)로 대화하게 함. 덤으로 한 집이 불나도 나머지는 멀쩡.

### Q16. GPU 메모리 문제는 없었나요? (아주 좋은 질문 — 실측 데이터가 있는 답변)
**답변:** 있었고, 원인 규명과 해결까지 했습니다.

RTX 4090 24.5GB에 백엔드 + uLayout + Omni3D가 함께 올라가면 여유 VRAM이 **2.4GB까지** 떨어집니다.
그 상태에서 프로세스 간 GPU 작업이 겹치자 **SAM3D의 decode 단계가 0.2초 → 67초로 튀는 것**을 실측했습니다.

원인을 추적해 보니, Stable Diffusion + ControlNet(fp16)이 **3~4GB를 상시 점유**하는데
정작 **세션당 딱 한 번, 7.6초** 쓰이는 모델이었습니다.

그래서 SD를 **서버 시작 시 로드하지 않고, 필요한 요청에서 로드했다가 끝나면 즉시 해제**하는 온디맨드 방식으로 바꿨습니다.
(`del` → `gc.collect()` → `torch.cuda.empty_cache()`)
로드 실패 시에도 LaMa 결과만으로 계속 동작하도록 예외 처리를 넣어, 품질만 조금 떨어질 뿐 기능은 유지됩니다.

**💡 쉽게 말하면:** 1년에 한 번 쓰는 짐이 방 한가운데를 차지하고 있었다. 그래서 창고에 넣고 필요할 때만 꺼내기로 함. 그랬더니 다른 작업이 300배 빨라짐.

### Q17. 그 외 성능 최적화는 어떤 걸 했나요?
**답변:** 병목을 측정하고 하나씩 제거했습니다.

1. **SAM2 이미지 인코딩 1회만 수행** — 가구를 여러 개 선택해도 `set_image()`는 한 번만 호출하고 포인트 프롬프트만 반복합니다. SAM의 무거운 연산은 이미지 인코딩이고 마스크 디코딩은 가볍기 때문에, 가구 N개일 때 N배가 아니라 거의 1배 시간으로 끝납니다.
2. **프론트에서 SAM2 재호출 스킵** — 클릭할 때마다 이미 미리보기 마스크를 받아왔으므로, "추출" 버튼을 눌렀을 때 모든 라벨의 미리보기가 준비돼 있으면 서버를 다시 부르지 않고 캔버스에서 마스크를 OR 합성해 재사용합니다.
3. **SAM3D seed 탐색 스텝 축소** — 아래 Q18 참고.
4. **3D 뷰 on-demand 렌더링** — 아래 Q19 참고.
5. **분석 3종 병렬 호출** — 색상 추출 / 방 치수 / 텍스처 rectify를 `Promise.allSettled`로 동시에 던집니다. 순차로 하면 셋을 더한 시간이 걸립니다.

**💡 쉽게 말하면:** 같은 사진을 매번 다시 분석하지 않게 하고, 동시에 할 수 있는 건 동시에 하고, 안 움직일 땐 그리지 않게 함.

### Q18. SAM3D 3D 변환 시간을 줄인 방법을 설명해 주세요.
**답변:** SAM3D는 seed(난수 시드)에 따라 결과 품질 편차가 큽니다. 어떤 seed는 납작한 판자가 나오고, 어떤 seed는 제대로 된 입체가 나옵니다.
그래서 원래는 **Stage1을 5번 돌려 가장 입체적인 seed를 고르고**, 그 seed로 Stage2 본 실행을 하는 구조였습니다.
- 입체성 점수: 일반 가구는 `voxel의 세 축 범위 중 최솟값`(가장 얇은 축이 두꺼울수록 입체적), 얇은 물체(조명/꽃/화분)는 `voxel 개수`

문제는 탐색 5회도 각각 25스텝을 돌아서 오래 걸렸다는 점입니다.
그런데 **탐색 패스는 "어느 seed가 제일 나은가" 순위만 보면 되고, 실제 최종 메쉬는 그 뒤 본 실행이 처음부터 다시 만듭니다.**
즉 탐색 결과물의 품질은 버려집니다. 그래서 **탐색만 10스텝으로 낮췄습니다**(환경변수 `SAM3D_SEARCH_STEPS`로 조절 가능, 25로 두면 종전 동작과 완전 동일).

**트레이드오프도 명시했습니다:** 거친 voxel로 순위를 매기게 되므로 선택되는 seed가 달라질 수 있습니다. 실사용 품질 차이는 체감되지 않는 수준이라 채택했습니다.

**💡 쉽게 말하면:** 5명 중 제일 잘하는 사람 뽑는 오디션인데, 오디션에서 부른 노래는 어차피 안 쓰고 뽑힌 사람이 다시 부른다. 그럼 오디션은 짧게 봐도 된다.

### Q19. 3D 뷰어가 무겁다고 하셨는데 어떻게 해결했나요?
**답변:** 두 가지입니다.

1. **메인 뷰 on-demand 렌더링** — 원래는 `requestAnimationFrame`으로 조작이 없어도 매 프레임(60fps) 방 전체(조명 3개 + 실사 텍스처 + 가구 메쉬)를 다시 그렸습니다. 이제는 마우스 조작 등에서 `invalidate()`가 호출된 뒤 **300ms 동안만** 렌더링합니다. 가만히 두면 GPU가 idle이 되고, 드래그·회전·줌 중에는 그대로 60fps가 나옵니다.
   - 한 프레임만 그리지 않고 300ms 여유를 둔 이유는, 지오메트리 추가나 텍스처 로딩이 다음 프레임에 걸쳐 반영되는 경우를 놓치지 않기 위해서입니다.
2. **가구 미니 뷰 정지** — 사이드바의 가구 썸네일도 각각 Three.js 씬입니다. `IntersectionObserver`로 화면 밖으로 스크롤되면 애니메이션을 멈추고, `document.hidden`(탭 전환)일 때도 멈춥니다.

**💡 쉽게 말하면:** 아무것도 안 하고 있는데 계속 그림을 다시 그리고 있었다. 움직일 때만 그리게 바꿈. 안 보이는 썸네일도 마찬가지.

### Q20. SAM3D로 "방" 자체도 3D로 만들려고 했다던데, 왜 안 쓰나요?
**답변:** 실제로 구현했고, 후처리도 꽤 많이 넣었습니다.
- `_flatten_room_mesh()` — SAM3D가 만든 벽·바닥이 울퉁불퉁해서, 바닥/뒷벽/좌벽/우벽 4면 근처(정규화 거리 0.28 이내) vertex를 해당 평면 쪽으로 최대 90% 당겨 평평하게 snap
- 천장·앞벽 face 제거 (안이 보여야 하므로)
- `trimesh`로 degenerate face 제거 + hole fill + 약한 Laplacian smoothing
- 바닥 커버리지가 40% 미만이면 바닥 평면을 강제로 삽입

그럼에도 **"실제 치수를 알 수 없다", "가려진 벽은 복원되지 않는다"** 는 근본 한계가 남았습니다.
인테리어 시뮬레이터는 방이 정확한 직육면체여야 배치와 충돌 계산이 신뢰할 수 있습니다.
그래서 최종적으로는 **uLayout이 추정한 실제 치수(m)로 Three.js 박스 방을 만들고, 그 표면에 원본 사진에서 rectify한 실사 텍스처를 입히는 방식**으로 전환했습니다. SAM3D 방 코드는 `room.py`에 남아 있고 API로도 살아 있습니다.

**💡 쉽게 말하면:** AI로 방을 통째로 3D화해 봤는데 울퉁불퉁하고 크기를 모른다. 그래서 "정확한 크기의 반듯한 상자"를 만들고 그 벽에 진짜 사진을 발라버리는 쪽이 훨씬 실용적이었다.

**이 답변이 좋은 이유:** 면접관은 "실패한 시도를 어떻게 판단하고 방향을 바꿨는가"를 좋아합니다. 실패가 아니라 **의사결정**으로 말하세요.

### Q21. 벽/바닥 텍스처는 어떻게 만드나요? (`_least_busy_patch`)
**답변:** 두 갈래입니다.
- **1순위: rectify** — uLayout이 방 코너를 검출하면, 원본 사진의 벽/바닥/천장 5개 면을 정면에서 본 것처럼 펴서(호모그래피) 실사 텍스처로 씁니다.
- **2순위: 패치 타일링 폴백** — 코너 검출이나 solvePnP가 실패하면, 사진에서 **가장 무난한 100×100 패치**를 하나 찾아서 타일처럼 반복합니다.

이 "무난한 패치 찾기"가 생각보다 까다로웠습니다. 세 가지 처리를 넣었습니다.
1. **de-lighting (flat-fielding)** — 가우시안 블러로 저주파 조명 성분을 추정하고 나눠서 그림자·조명 그라데이션을 제거합니다. 남는 건 실제 재질 무늬(고주파)뿐입니다. 그 **잔차(residual) std가 가장 작은 패치**를 고릅니다.
2. **글레어 제외** — 채널값 245 이상인 픽셀은 정보가 날아간 영역이라 후보에서 뺍니다.
3. **SAM2 마스크 재사용** — 가구를 지울 때 쓴 마스크를 그대로 넘겨 "가구가 있던 자리"를 후보에서 제외합니다. 안 그러면 블라인드 그림자나 침대 밑처럼 분산은 낮지만 벽이 아닌 영역이 뽑혔습니다.

그리고 잔차 std가 임계값(18.0)보다 낮으면 "무늬가 없는 매끈한 벽"으로 보고 타일링 대신 **평균색 단색**으로 채웁니다. 무늬 없는 걸 타일링하면 반복 이음새가 줄무늬로 튀어서 오히려 더 부자연스럽기 때문입니다.

**💡 쉽게 말하면:** 벽지 무늬를 복사해서 도배하려는데, 그림자 진 부분을 복사하면 그림자가 반복돼서 이상해진다. 그래서 먼저 조명 효과를 지우고 → 진짜 무늬만 남기고 → 그중 제일 얼룩 없는 조각을 고른다. 무늬가 아예 없으면 그냥 단색으로 칠한다.

### Q22. 그 임계값 18.0은 어떻게 정했나요? (하드코딩 지적 대비)
**답변:** **실측으로 잡았습니다.**
꽃무늬 벽지의 raw std가 약 26.65(패턴 있음), 그라데이션만 있는 무지 벽이 약 13.57(패턴 없음)로 나와서 그 사이인 18.0으로 잡았습니다.
de-light 커널 크기(21px)도 같은 방식입니다 — k=9일 때 꽃무늬 벽지의 잔차 std가 16.98로 떨어져 임계값 아래로 잘못 내려갔고(무늬를 조명으로 오인해 지워버림), k=21에서 20.96으로 정상 유지되어 21을 택했습니다.

다만 **샘플 수가 적어 일반화가 부족하다는 건 알고 있습니다.** 그래서 코드에 `*** NEEDS TUNING WITH REAL DATA ***` 주석과 실측 근거를 남겨 두었고, 추후 데이터가 쌓이면 조정하도록 상수로 분리했습니다.

**💡 쉽게 말하면:** 눈대중으로 정한 게 아니라 몇 장 찍어서 숫자를 재고 그 사이값으로 잡았다. 다만 표본이 적은 건 인정하고, 나중에 고치기 쉽게 상수로 빼놨다.

**이 답변이 좋은 이유:** 하드코딩 상수는 면접에서 잘 찔립니다. **"근거가 있고, 한계를 알고, 고칠 수 있게 만들어놨다"** 면 오히려 가산점입니다.

### Q23. 좌표계 관련 버그가 있었다고요?
**답변:** 세 가지 겪었습니다. 전부 "같은 점을 다른 자로 재던" 문제입니다.

1. **EXIF 회전** — 스마트폰 사진은 실제 픽셀은 가로인데 "세로로 돌려서 보라"는 EXIF 회전 정보가 따로 들어 있습니다. 브라우저는 이걸 자동 적용해서 세로로 보여주는데, 백엔드 PIL은 적용하지 않아 **클릭 좌표와 마스크 위치가 어긋났습니다.** `ImageOps.exif_transpose()`로 회전을 픽셀에 실제 반영해 해결했습니다.
2. **리사이즈 좌표계** — 서버는 처리 속도를 위해 이미지를 1024px로 줄입니다. 그런데 bbox를 리사이즈된 좌표 그대로 반환했더니, 프론트가 그 bbox로 **원본 해상도 사진**을 크롭할 때 엉뚱한 영역을 잘랐습니다. `extract.py`에서 `bbox / scale`로 원본 좌표계로 환산해서 반환하도록 고쳤습니다.
3. **Y축 방향** — SAM3D(PyTorch3D)와 Three.js는 Y축 부호 규약이 다릅니다. 메쉬를 프론트로 넘길 때 Y를 반전(`-y`)합니다. 안 하면 방이 뒤집혀 보입니다.

**💡 쉽게 말하면:** 같은 사진인데 브라우저는 세로로 보고 서버는 가로로 봐서, 클릭한 곳과 다른 데가 잘렸다. 그리고 서버는 작게 줄여서 보는데 그 좌표를 원본에 그대로 쓰면 딴 데를 자른다. 마지막은 3D 라이브러리마다 "위쪽"의 부호가 반대라서 방이 뒤집혔다.

### Q24. 납작한 물체(액자, 시계)가 3D 변환이 잘 안 됐다면서요?
**답변:** SAM3D가 액자·거울처럼 얇은 물체를 거의 **두께 0의 종이**로 만들어서 3D 뷰에서 안 보이는 문제가 있었습니다. 두 가지로 대응했습니다.

1. **Shape prior 주입** — 카테고리에 따라 대략적인 3D 형태 힌트(pointmap)를 만들어 SAM3D에 함께 넣습니다. 액자·거울은 가장자리가 살짝 뒤로 가는 원반형, 조명·꽃·화분은 아래가 더 가까운 원뿔형으로 depth를 줍니다.
2. **후처리 z축 강제 부풀리기** — 그래도 얇으면, 메쉬 세 축 중 가장 얇은 축을 찾아 **가장 긴 축의 25% 또는 최소 5cm**까지 중심 기준으로 확대합니다.

**💡 쉽게 말하면:** AI가 액자를 종이짝처럼 얄팍하게 만들어서 옆에서 보면 안 보였다. 그래서 "액자는 대충 이런 모양이야"라고 힌트를 주고, 그래도 얇으면 강제로 살을 붙였다.

# D. 프론트엔드 / 3D

### Q25. 3D 라이브러리로 왜 Three.js를 직접 썼나요? react-three-fiber는요?
**답변:** 저희는 `useEffect` 안에서 Three.js 씬을 직접 만들고 `ref`로 관리합니다.
이유는 **렌더 루프를 저희가 완전히 통제해야 했기 때문**입니다. on-demand 렌더링(Q19), 드래그 중 raycasting, 충돌 판정, 미니뷰 정지 제어 같은 것들을 프레임 단위로 직접 다뤄야 했습니다.
react-three-fiber는 선언적이라 개발 속도는 빠르지만, React 리렌더 사이클과 렌더 루프가 얽히면 저희가 원하는 세밀한 제어가 어려웠습니다.

**💡 쉽게 말하면:** 편한 자동 모드 대신 수동 모드를 골랐다. 언제 그릴지를 우리가 정해야 최적화가 되니까.

---

### Q26. 가구 배치할 때 충돌 감지는 어떻게 하나요?
**답변:** **AABB(축 정렬 바운딩 박스) 겹침 검사**입니다.
드래그 중 매 이동마다, 이동시킨 가구와 다른 모든 가구의 박스가 X·Z(바닥 평면)와 Y(높이) 모두에서 겹치는지 확인합니다.
겹치면 **이전 위치로 되돌립니다**(`prevX`, `prevZ` 복원). 그래서 가구가 서로 뚫고 지나가지 못합니다.
여유값 0.04m를 빼서 살짝 스치는 정도는 허용했습니다 — 안 그러면 벽에 딱 붙이는 게 불가능해집니다.

추가로 **"다른 가구 위에 올려놓기"** 도 지원합니다. raycasting으로 맞은 면의 법선이 위를 향하면(`normal.y > 0.5`) 바닥이 아니라 그 면 위에 얹습니다. 책상 위에 조명을 올리는 식입니다.

**💡 쉽게 말하면:** 가구를 상자로 단순화해서 상자끼리 겹치면 못 가게 막는다. 대신 위쪽 면에 놓는 건 허용 — 책상 위에 스탠드 올리기.

**꼬리질문 대비 — 왜 물리엔진(cannon-es)을 안 썼나요?**
> 초기 `web/` 버전에서는 cannon-es를 썼는데, 인테리어 배치는 "가구가 굴러다니면" 안 됩니다. 사용자가 놓은 자리에 정확히 멈춰 있어야 하므로, 물리 시뮬레이션보다 단순 AABB 검사 + 위치 롤백이 UX에 맞았습니다.

---

### Q27. 상태 관리는 어떻게 했나요?
**답변:** **zustand**를 썼습니다. 4단계 화면이 원본 사진, 마스크, 빈 방 이미지, 가구 리스트, 방 치수, 카메라 pose 등을 공유해야 하는데,
props로 넘기면 4단계를 관통하는 prop drilling이 됩니다. Redux는 이 규모에 보일러플레이트가 과했습니다.

추가로 3D 배치 화면에는 **undo/redo**를 스냅샷 배열 + 인덱스 방식으로 구현했고,
완성된 디자인은 **IndexedDB**에 저장합니다(메쉬 데이터가 커서 localStorage로는 용량이 부족).

**💡 쉽게 말하면:** 화면 4개가 같은 데이터를 봐야 해서 전역 저장소를 씀. Redux는 이 규모엔 과해서 가벼운 zustand.

### Q28. 마스크 미리보기는 어떻게 실시간처럼 보이게 했나요?
**답변:** 클릭할 때마다 서버를 부르면 클릭이 빠를 때 요청이 쌓입니다. 그래서 **300ms 디바운스**를 걸었습니다.
마지막 클릭 후 300ms 동안 추가 클릭이 없으면 그때 SAM2를 호출합니다.
받은 마스크는 라벨별 색을 입혀 오프스크린 캔버스에서 픽셀 단위로 색을 바꾼 뒤 원본 위에 합성합니다.

**💡 쉽게 말하면:** 연타로 클릭해도 마지막 한 번만 서버에 물어보게 함.

# E. 성능 평가 / 검증

### Q29. 성능은 어떻게 측정했나요? (준비 필수 — 정량 지표를 물어봅니다)
**답변:** SAM2 분할 성능은 **정량 평가 스크립트**(`web/backend/evaluate.py`)를 만들었습니다.
- 침대·의자·책상 각 4장씩 12장에 대해 **LabelMe로 GT 폴리곤을 직접 라벨링**했습니다.
- 지표는 두 가지입니다:
  - **Coverage(재현율)** = GT 영역 중 SAM이 잡아낸 비율 → 가구를 놓치지 않았는가
  - **Precision(정밀도)** = SAM이 잡은 영역 중 실제 가구인 비율 → 배경까지 잡지 않았는가
- 임계값 0.8을 기준으로 성공/실패를 판정했습니다.

**Coverage를 중요하게 본 이유**를 설명하면 좋습니다: 가구 일부를 놓치면 그 부분이 빈 방에 유령처럼 남기 때문에, 저희 파이프라인에서는 재현율이 정밀도보다 치명적입니다. 그래서 마스크에 dilate를 15px 적용해 일부러 조금 넉넉하게 잡습니다.

그 외에는 각 단계마다 처리 시간 로그(`[⏱ 처리시간]`)를 남겨 병목을 추적했습니다. SD 로드 7.6초, LaMa 인페인팅, SAM3D Stage1/Stage2 등이 전부 측정됩니다.

**💡 쉽게 말하면:** 정답 마스크를 손으로 그려놓고, AI가 그린 것과 얼마나 겹치는지 비율로 쟀다. "빠뜨리지 않는 것"이 "넘치지 않는 것"보다 중요해서 일부러 조금 넉넉하게 잡게 했다.

**⚠️ 면접 전에 꼭 할 일:** `python evaluate.py`를 돌려서 **실제 수치를 외워 가세요.** "coverage 평균 0.9X" 같은 숫자 하나가 답변 신뢰도를 크게 올립니다.

### Q30. 전체 처리에 시간이 얼마나 걸리나요?
**답변:** 단계별로 로그를 남겨 측정했습니다.
- SAM2 분할: 수 초 (이미지 인코딩 1회 재사용으로 가구 개수와 거의 무관)
- LaMa + SD 빈 방 생성: SD 로드 약 7.6초 + 추론 (세션당 1회)
- SAM3D 가구 1개 3D 변환: Stage1 탐색 5회 + Stage2 본 실행 — 가장 무거운 구간이고, 탐색 스텝을 25→10으로 줄여 단축했습니다.

**솔직하게 말할 부분:** 3D 변환이 여전히 실시간이라고 하기는 어렵습니다. 그래서 UX 상 가구별로 사용자가 원할 때 하나씩 변환하도록 했고, 변환 중에도 다른 조작이 가능하도록 비동기로 처리했습니다.

**💡 쉽게 말하면:** 3D 만드는 게 제일 오래 걸린다. 그래서 "전부 한꺼번에"가 아니라 "필요한 가구만 하나씩" 변환하게 UX를 짰다.

# F. 한계와 개선 방향 (반드시 준비)

### Q31. 이 프로젝트의 한계는 무엇인가요?
**답변:** 솔직하게 네 가지로 정리합니다.
1. **가려진 부분은 복원할 수 없습니다.** 사진 한 장이므로 소파 뒷면은 정보 자체가 없어 SAM3D가 추정해서 채웁니다.
2. **가구 크기 추정 정확도가 사진 조건에 의존합니다.** 방 코너가 안 보이면 uLayout의 solvePnP가 실패해 근사 pose(가정 카메라 높이 1.6m)로 폴백하고, 그만큼 오차가 커집니다.
3. **텍스처 판정 임계값이 소수 샘플 기반**입니다(Q22).
4. **3D 변환 속도**가 실시간이 아닙니다.

**💡 쉽게 말하면:** 사진 한 장의 한계(안 보이는 뒷면), 사진 잘 찍어야 잘 나옴, 튜닝 값 표본 부족, 느림.

### Q32. 더 개선한다면 무엇을 하시겠습니까?
**답변:**
1. **여러 장 입력 지원** — 방을 2~3장 찍으면 가려진 면 정보가 생겨 3D 품질과 치수 정확도가 함께 올라갑니다. 다만 "한 장이면 된다"는 장점과의 트레이드오프가 있어 옵션으로 둘 것 같습니다.
2. **3D 변환 큐/캐싱** — 같은 가구를 다시 변환하지 않도록 결과를 캐싱하고, 백그라운드 작업 큐(Celery 등)로 빼서 사용자가 기다리지 않게 하겠습니다.
3. **자동 라벨링** — 지금은 사용자가 가구 종류를 직접 고릅니다. Grounding DINO 같은 open-vocabulary 탐지기를 붙이면 클릭만으로 카테고리를 자동 판정할 수 있습니다.
4. **크기 추정 평가셋 구축** — 지금 분할(SAM2)만 정량 평가가 있는데, 실측 줄자로 잰 가구 크기 데이터셋을 만들어 4단계 폴백 체인 각각의 오차를 측정하고 싶습니다.

**💡 쉽게 말하면:** 사진 여러 장 받기 / 3D 변환 미리 돌려놓기 / 가구 이름 자동으로 맞히기 / 크기 정확도도 숫자로 재기.

### Q33. 실제 서비스로 배포한다면 무엇이 문제가 될까요?
**답변:** GPU 비용과 동시성입니다.
지금은 로컬 GPU 1대에 모델 4종이 올라가 있어 **동시 사용자 1명 기준** 구조입니다.
서비스화하려면 (1) 모델 서빙을 API 서버와 분리하고, (2) 요청 큐를 두고, (3) GPU 인스턴스를 오토스케일해야 합니다.
지금 사이드카 패턴으로 프로세스를 이미 분리해 뒀기 때문에, 각 사이드카를 독립 컨테이너로 옮기는 방향으로는 확장이 비교적 자연스럽습니다.

**💡 쉽게 말하면:** 지금은 내 컴퓨터 한 대에 다 올려서 한 명만 쓸 수 있음. 진짜 서비스면 GPU 서버를 따로 두고 줄 세워야 함. 다만 이미 프로세스를 나눠놔서 옮기기는 수월함.

### Q35. 협업하면서 어려웠던 점은?
**답변 방향:** 노트북(Jupyter) 실험 코드를 서비스 코드로 옮기는 과정이 가장 컸습니다.
각자 노트북으로 모델을 실험했는데, 그걸 그대로 합치면 전역 상태와 `os.chdir` 같은 부작용이 충돌합니다.
그래서 모델마다 **서비스 클래스**(`SAM2Service`, `LamaService`, `SDService`)로 감싸고, FastAPI `lifespan`에서 앱 시작 시 한 번 로드해 `app.state`에 보관하는 구조로 통일했습니다.
로드에 실패한 모델은 `None`으로 두고, 해당 라우터가 `503`을 반환하도록 해서 **모델 하나가 죽어도 서버 전체는 뜨도록** 만들었습니다.

**💡 쉽게 말하면:** 각자 주피터에서 실험한 코드를 합치려니 서로 충돌해서, 모델마다 껍데기 클래스를 씌워 규격을 통일했다. 하나 고장 나도 서버는 뜨게 함.

| **세그멘테이션(분할)** | 사진에서 "이 픽셀은 소파, 저 픽셀은 벽" 하고 오려내는 것 |
| **마스크** | 오려낸 결과를 흑백 이미지로 표현한 것 (흰색 = 가구, 검정 = 배경) |
| **인페인팅** | 지운 부분을 주변과 자연스럽게 메꾸는 것 (포토샵 '내용 인식 채우기') |
| **메쉬(mesh)** | 3D 모델. 점(vertex)들을 삼각형(face)으로 이어 만든 껍데기 |
| **vertex color / UV 텍스처** | 3D 모델에 색을 입히는 두 방식. 전자는 점마다 색, 후자는 사진을 껍데기에 감싸는 방식 |
| **voxel** | 3D 픽셀. 공간을 정육면체 격자로 쪼갠 것. SAM3D Stage1 결과물 |
| **bbox** | 물체를 감싸는 최소 사각형. `[y0, y1, x0, x1]` |
| **solvePnP** | 사진 속 점들의 실제 3D 위치를 알 때, 카메라가 어디서 어떤 각도로 찍었는지 역산하는 OpenCV 함수 |
| **핀홀 카메라 모델** | 카메라를 "바늘구멍"으로 단순화한 모델. `픽셀크기 = 실제크기 × 초점거리 / 거리` |
| **rectify** | 비스듬히 찍힌 면을 정면에서 본 것처럼 펴는 것 |
| **ControlNet** | 이미지 생성 모델에 "이 선을 지켜라" 같은 조건을 추가로 거는 보조 모듈 |
| **Canny** | 이미지에서 윤곽선만 뽑아내는 고전 알고리즘 |
| **dilate / morphology** | 마스크를 조금 부풀리거나(dilate) 구멍을 메우는(close) 이미지 처리 연산 |
| **raycasting** | 마우스 위치에서 3D 공간으로 가상의 광선을 쏴서 뭐가 맞는지 찾는 것 |
| **AABB** | 축에 정렬된 사각 상자. 충돌 판정을 가장 싸게 하는 방법 |
| **fp16** | 16비트 부동소수점. 모델 정밀도를 절반으로 줄여 GPU 메모리와 속도를 아끼는 것 |
| **사이드카 패턴** | 메인 서버 옆에 보조 프로세스를 따로 띄우고 HTTP로 통신하는 구조 |
| **폴백(fallback)** | 1순위 방법이 실패하면 2순위, 3순위로 자동으로 넘어가는 설계 |

- [ ] `./scripts/services.sh start`로 실제 데모가 돌아가는지 확인 (시연 요청 대비)
- [ ] `evaluate.py` 실행해서 **coverage/precision 실제 수치 외우기**
- [ ] 30초 요약(맨 위)을 소리 내어 3번 연습
- [ ] **본인 담당 파트**를 명확히 정하고, 그 부분은 코드 레벨까지 설명 가능하게
- [ ] Q11~Q16(크기 추정 + GPU 메모리)은 가장 자주 파고드는 부분 — 반드시 준비

## 면접에서 가장 강조하면 좋을 3가지

1. **폴백 설계 능력** — 크기 추정 4단계, 텍스처 2단계, 사이드카 다운 시 graceful degradation. "안 될 때를 설계했다"는 건 실무자 마인드입니다.
2. **측정 기반 최적화** — GPU 여유 2.4GB → SAM3D 0.2초가 67초로. 감이 아니라 **숫자로 원인을 찾고 고쳤다**는 이야기.
3. **실패한 시도를 판단해서 방향을 바꿈** — SAM3D 방 생성을 포기하고 uLayout 치수 + 박스 방 + 실사 텍스처로 전환한 의사결정.
